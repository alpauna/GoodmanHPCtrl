# Bug #3: Config-loaded sensors marked valid on boot — stale 0.0°F triggers false LOW_TEMP protection

**Severity:** High (safety)
**Date discovered:** 2026-02-26
**Affected file:** `src/Config.cpp`
**Fixed in:** `d49d2e8` ("Fix false LOW_TEMP on boot from stale config-loaded sensor values")

---

## Summary

When the system boots, temperature sensors loaded from the SD card config are immediately marked as `valid=true` with their cached `last-value` from the previous session. If that cached value is 0 (no prior reading stored) or stale, the value 0.0°F passes the `isValid()` check and triggers `checkAmbientTemp()` — which sees 0.0°F < 20°F (or 25°F) threshold and activates LOW_TEMP protection. This shuts down CNT, turns off FAN and RV, and turns on W (auxiliary heat) — all before the first real OneWire bus read occurs ~10 seconds after boot.

## Impact

- Every reboot during an active HEAT cycle falsely triggers LOW_TEMP protection
- W (auxiliary electric heat) turns on unnecessarily for ~10 seconds until real sensor data arrives
- CNT (compressor contactor) is blocked during this window, delaying normal operation
- In the log analysis, **77 false LOW_TEMP triggers** were recorded across 263 reboots (Feb 8–26), all reading **0.0°F** as the ambient temperature
- One instance recorded **-196.6°F** (OneWire CRC error / `DEVICE_DISCONNECTED_F`) which also triggered LOW_TEMP with W turned on, self-correcting 21 seconds later when the sensor returned 185.0°F

## Incident Timeline (from log analysis)

Observed on virtually every reboot during Feb 8–15 (263 reboots total). Example sequence:

| Time | Event | Ambient Temp |
|------|-------|:------------:|
| Boot | Outputs verified OFF, startup lockout begins | — |
| +0s | Config loads AMBIENT_TEMP from JSON with `last-value: 0`, marks `valid=true` | 0.0°F (stale) |

## Root Cause Analysis

### The bug: `setValid(true)` on config-loaded sensors

In `Config::loadTempConfig()` (Config.cpp:556–558), sensors loaded from the `sensors.temp` JSON section are unconditionally marked valid:

```cpp
sensor->setValue(last_value);       // Sets _valid = (value != DEVICE_DISCONNECTED_F)
sensor->setPrevious(sensor->getValue());
sensor->setValid(true);             // Overrides to valid — even if value is stale/zero
```

`setValue()` already sets `_valid = true` for any value other than `DEVICE_DISCONNECTED_F` (-196.6°F). The explicit `setValid(true)` reinforces this. A `last-value` of 0 (the JSON default when no prior reading exists) passes both checks.

### Why the protection code doesn't catch it

`checkAmbientTemp()` (GoodmanHP.cpp:251) correctly guards with:

```cpp
TempSensor* ambient = getTempSensor("AMBIENT_TEMP");
if (ambient == nullptr || !ambient->isValid()) return;
```

But since `isValid()` returns `true` for the stale config-loaded sensor, the guard passes. The 0.0°F value is then compared against the threshold and triggers LOW_TEMP.

### Why 0 is the common cached value

The `last-value` field in the config JSON is written by `saveConfiguration()` using `mp.second->getValue()`. On the very first boot (before any OneWire reading), or after a reboot where the sensor never got a valid reading before the next save, the value is 0.0 (the `TempSensor` constructor default). This 0 is persisted to JSON and reloaded on the next boot.

### All temp-based protections are affected

The same pattern applies to every temp-based protection check:
- `checkAmbientTemp()` — LOW_TEMP (0.0°F < 25°F threshold)
- `checkCompressorOverTemp()` — would NOT false-trigger (0.0°F is below the high threshold)
- `checkSuctionLowTemp()` — could false-trigger in COOL mode (0.0°F < suction threshold)

## Fix Applied

Single line change in `src/Config.cpp`:

```cpp
// Before:
sensor->setValue(last_value);
sensor->setPrevious(sensor->getValue());
sensor->setValid(true);

// After:
sensor->setValue(last_value);
sensor->setPrevious(sensor->getValue());
sensor->setValid(false);  // Not valid until first real bus read
```

Config-loaded sensors now start as `invalid`. The `isValid()` guard in all protection checks (`checkAmbientTemp`, `checkCompressorOverTemp`, `checkSuctionLowTemp`) causes them to return early without action. On the first real bus read (~10s after boot), `TempSensor::update()` sets `_valid` based on the actual reading, and protection checks resume with real data.

## Files Changed

- `src/Config.cpp` — `loadTempConfig()`: `setValid(true)` → `setValid(false)`

## How to Reproduce

1. Ensure `sensors.temp` in the SD card config has an AMBIENT_TEMP entry with `last-value: 0`
2. Set `heatpump.lowTemp.threshold` to any value above 0 (e.g., 25°F)
3. Reboot the device
4. **Before fix:** LOW_TEMP activates within 500ms of boot, W turns on, clears ~10s later when real sensor data arrives
5. **After fix:** No LOW_TEMP trigger on boot. Sensors show as `valid=false` in `/temps` for the first ~10s, then become valid with real readings

## Lessons Learned

- Cached/persisted sensor values should never be trusted for safety decisions — mark sensors invalid until confirmed by a real physical read
- The `isValid()` guard pattern is effective but only works if validity accurately reflects whether the value came from the physical device
- A `last-value` of 0 in config JSON is indistinguishable from a real 0°F reading — validity should be based on provenance (real read vs cached), not just value range
- This bug was latent for the entire deployment but masked after Feb 15 when the device stopped rebooting — it would resurface on any future reboot during a HEAT cycle
